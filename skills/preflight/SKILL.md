---
name: preflight
description: Check documents before an audit and apply only the fixes the user approves.
argument-hint: "[--deep] [--full] [--profile focused|standard|extended]"
---

利用者の言葉で結果を伝え、修正の承認を得る。既定では組み込み検査の所見をもとに直し案を作る。`--deep` を指定したときだけ、監査の判定基準でも文書を読む。

1. `$ARGUMENTS` にオプションとして `--deep` があれば、深い点検を選び、`--deep` を取り除く。残りの引数を順序と引数ごとの区切りを保って、次の命令の末尾に付けて実行する。終了値が `0` または `3` なら、出力の最終行を JSON として読む。`3` なら `reason` の内容を平易に伝えて終了する。終了値が `0` と `3` のいずれでもなければ、出力をそのまま示して終了する。引数の誤りで JSON が出ないときも同じ。

   ```sh
   python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/audit/engine" precheck
   ```

2. `impacted` に含まれる文書の件数と `checks` の所見を示す。`checks` は監査と同じ組み込み検査の結果で、監査対象の文書全体（corpus）を調べるため、`impacted` の外の文書の所見も含む。監査では対象のどの文書でも、所見が `FAIL` なら修正が必要になる。`projectLayer` が `false` なら、このプロファイルでは組み込み検査を実施しないと伝える。`projectChecksSkipped` が 0 より大きければ、実行を省いた追加検査の件数も示す。

   エンジンの記録先である `.claude/state/docaudit/` の下を指すパス語が検査対象になり、点検時に参照先が存在しなければ、参照先が見つからないという所見が出る。監査は実行記録を開いてから検査するため、その時点で作られた参照先には同じ所見が出ないと伝える。この所見は直し案に含めない。

3. `--deep` を指定したときは、先に下の「深い点検」の手順を行う。会話モデルは `checks` の所見から直し案を作る。`--deep` のときは、深い点検で見つけた食い違いからも直し案を作る。所見には修正後の参照先の候補も行番号も入っていないため、モデルが該当箇所と参照先を調べる。文書の修正で解消する所見は `a` として直し案を示してよい。対象の例は壊れたリンクと参照先が見つからないパス語。これは `impacted` の外にある監査対象の文書にも適用する。手順 2 の記録先に関する所見は除く。直し案の対象を分類し、次の列を持つ表で利用者に示す。

   | 文書の `file:line` | 文書の言い切り | 実物の `file:line` と中身 | 分類 | 直し案 |
   | --- | --- | --- | --- | --- |

   - `a` は現状と比べて文書が古い箇所、`b` は予定を現状として書いた箇所。いずれも修正前と修正後の文を示す。
   - `c` は仕様と実装のどちらが正しいか、利用者の裁定が必要な箇所。
   - `U` はリポジトリの中で確かめられない記述。別の一覧に示すだけとし、修正しない。

   質問用の道具を使い、`checks` の所見（`--deep` のときは判定の基準による食い違いも）から示した直し案のうち、どれを承認するか利用者に尋ねる。`c` の項目は文書を直すか、実装を直す別の作業にするかを必ず利用者に決めてもらう。承認が得られるまで編集しない。
4. 承認された箇所だけを直す。判定の基準による食い違いは `impacted` の文書、`checks` の所見は監査対象の文書（corpus）に限って直す。コード、設定、試験は編集しない。変更した語や値を他の文書でも検索する。表記や値を揃える案があれば、対象文書の修正について手順 3 と同じように改めて承認を得る。
5. 手順 1 で実行した `precheck` を同じ引数でもう一度実行し、残っている組み込み検査の所見を示す。最後に `/docaudit:audit` の実行を勧める。

この手順では `audit` と `resume` を実行しない。Git への書き込みは行わない（例は `git add` と `git commit`）。修正後に「監査に合格した」と伝えない。

## 深い点検（`--deep`）

`${CLAUDE_PLUGIN_ROOT}/agents/doc-impact-verifier.md` を読み、`<verdict_criteria>` 内の要素を使う。`projectLayer` が `true` なら、監査の判定役と同じように、同じファイルの `<links>` 要素を `<evidence>` の直前に加える。基準の文言は変えず、`impacted` の文書ごとに当てる。根拠には Git が追跡するファイルだけを使う。`runId` や `judgementPath` を扱う手順と `cat > ...` による判定の保存は監査専用なので、ここでは行わない。判定結果はファイルに保存せず、手順 3 の表に使う。文書が多いときは、文書を分けて複数の内部調査担当に同時に任せてよい。各担当に基準ファイルのパス、担当する文書、`<links>` を適用するかどうかを伝え、編集や判定結果のファイルへの書き出しを禁じる。
